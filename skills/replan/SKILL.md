# Replan

Leave the selected work easier to understand and act on: a plan consistent with accepted intent and
evidence, meaningful progress, and current derived views. Carry justified corrections through to the
authoritative files and local rebuild; do not stop at a list of suggestions when the requested scope
authorizes reversible plan maintenance. Scale depth to the selected projects and areas, not repository count
or a fixed ceremony.

## Establish scope and authority

Read workspace instructions/decision records, each relevant repository's own instructions and purpose,
and the canonical purpose document for each selected project or area. Locate actual task authority,
evidence locations, dashboard inputs/build rules, and the declared schema. Do not assume folder names,
a particular workspace path, or GitHub access.
If no workspace scope is specified, start with the current repository; ask before an unbounded scan.

For a portfolio request, inventory the configured roots/allowlist and classify sources as managed,
legacy under review, idea-stage, or explicitly excluded. Give each in-scope repository proportionate
coverage and report any uninspected scope; do not imply a complete portfolio audit from a sample.
Distinguish the workspace folder, repository boundary, project identity, and ongoing area. Several
projects may share a monorepo; inventory selected project directories and their purpose/task/evidence
sources, not just Git roots. A shared root index links those authorities without duplicating their state.
Repository-wide instructions and privacy/access rules apply to every included project, while project
contracts remain distinct. Shared Git activity is not evidence that each project progressed; check
project-specific artifacts and avoid letting an optional whole-repository recency field imply otherwise.
Legacy review may reveal reusable work without enrolling, moving, or rewriting those repositories.
Honor exclusions even when old maps/notes still mention them. Do not recursively read private originals
or secrets: use allowed plans, public project metadata, code, and evidence references. Existing private
boundaries continue to apply; relevance alone does not authorize reading restricted material.

Record the starting branch/revision, working changes, source authority, and relevant browser-draft state
when available. Inspect relevant uncommitted edits as evidence; preserve them. No stash/reset/cleanup or
replacement of unrelated work. If competing authorities cannot be reconciled, isolate that conflict
and continue independent work; do not silently choose the convenient copy.

A replan request normally authorizes reversible local plan/task corrections within its scope, including
useful restructuring. It does not authorize repository mergers/moves, component extraction into code,
new repositories, bulk implementation, commits/pushes, hosted publication, production actions, knowledge
uploads, purchases, or reading protected documents. Follow any additional explicit authorization already
given, but do not add blanket approval rituals for routine plan edits. Surface genuine scope/value
decisions as concise open questions while completing the rest. This skill is on demand, not monitoring.

## Audit reusable-product portability and privacy

For each in-scope shareable product/template repository, inspect the working tree, tracked and staged
file inventories, and prospective build/share inputs. Cover relevant docs/examples, fixtures/tests,
configuration, generated HTML/JSON, screenshots/assets, and embedded data. Look for actual personal
projects/status/feedback, copied knowledge, hardcoded personal paths/accounts, and private source data.
Use bounded inspection and minimal path/category evidence; do not reproduce secrets or read protected
originals merely to perform this audit. Keep detailed findings in private workspace notes outside the
product. Generic skill/product documentation must not absorb the personal findings.
This separation holds in any layout: placing private material in a product subfolder does not make it
safe to share the product repository. A private portfolio monorepo and a reusable product have different
publication boundaries. Check the full containing repository's intended upload, not just one project folder.

This is a hard write boundary: a reusable product contains generic code/contracts/recipes, configurable
roots, and fictional examples, not its user's real maps, decisions, feedback, or source configuration.
If personal task authority is still bundled inside the product, do not add/update those facts there,
even when an older maintenance instruction says to keep bundled maps current. Flag the misplaced
authority, propose the smallest reversible migration, and continue independent generic or correctly
located plan work. Do not silently delete/move data, rewrite history, or perform an unrequested migration.

Check again after edits and any authorized rebuild. If the builder would put private payloads inside the
product, do not regenerate them there; report the blocked refresh and required separation rather than
claiming the dashboard is current. Keep sensitive originals outside any dashboard payload. Do not claim
a privacy pass while violations remain. A clean current tree alone does not establish public-release
readiness: earlier Git history, exports, and releases may retain private data. Identify the need for a
deliberate history review or clean release process without rewriting history or publishing automatically.

## Reconcile intent with evidence

Before mutations, apply the product boundary above; an authoritative file can still be in the wrong place.

For each relevant contract, connect accepted purpose/principles and success criteria to current code or
artifacts, prior evaluations, revisions, and the recorded state. Locate actual domain/philosophy sources;
do not reconstruct them from a slogan. Use a compact private working note if needed, not a new parallel
task database. Distinguish observation, inference, proposal, and accepted decision.

| Evidence situation | Appropriate action |
|---|---|
| Relevant check/result proves the accepted contract at the applicable revision | Record verified state with the actual result/source; retain provenance. |
| A commit message, file presence, checked steps, or an unrelated passing test is the only support | Do not treat it as proof of the finish line. Inspect or run a relevant permitted evaluation; keep uncertainty visible. |
| Earlier verified work no longer proves changed requirements | Preserve the old result/date and explain its scope; mark affected built work for revalidation using supported state (such as `drift`). |
| Requirements, ownership, or milestone were only proposed | Keep them provisional. Do not invent acceptance criteria, active commitment, or a task graph to make the map look complete. |
| Evidence is missing, inaccessible, or contradictory | State the limitation and the smallest useful investigation/decision; do not fabricate a check, completion, count, or recency. |

Inspect a check before running it; choose bounded relevant local evaluations and honor their side effects.
Reuse valid evidence when the contract/revision is unchanged. Capture failures as evidence, not a prompt
to implement unrelated code until tests pass. A new build or a recently edited document is not proof that
every plan has been reconciled. Where supported, keep source revision, evaluation/replan, and build
freshness distinct; otherwise explain those boundaries in existing notes rather than inventing fields.

## Improve the plan and the experience

Look beyond the requested feature to the person's actual workflow:

- Finite cases need finish lines; ongoing responsibilities need meaningful review criteria. Completing
  a case does not finish its umbrella area. Do not invent recurring tasks or fake completion targets to
  manipulate progress. Discover status meanings, not just the allowed enum: a value meaning verified
  and scheduled must not be repurposed to mean merely ongoing. If the vocabulary cannot express area
  health, retain that limitation explicitly instead of redefining a status in a note or implying evidence.
  Explain current renderer limitations when it cannot represent that distinction.
- Make next actions easy to locate and understand visually with little reading. Remove avoidable
  organization/maintenance burden; a more elaborate graph is not automatically a better plan.
- Split or consolidate work when accepted contracts, independent evaluation, or dependency scope justify
  it. Keep useful milestones incremental. Add detail only where supported; preserve ideas as ideas.
- Look for reusable capabilities across the allowed scope. Specify the consumer's required contract,
  relevant evidence/version, gaps, and limitations. A completed capability can be usable while its broader
  project is incomplete; do not mark the whole provider complete or gate on all its unrelated future work.
  Code extraction or repository consolidation stays a proposal unless separately authorized.

Use dependencies for true prerequisites, not association or data flow. Respect supported relation scope
and reject cycles. Under a sibling-only schema, do not invent cross-scope path IDs or new relation fields.
Find a truthful representable contract if possible; otherwise document the limitation and a proposal.
Do not silently erase a real prerequisite simply to make work ready. Inspect both direct and inherited
gates, and don't let a recorded completion with an incomplete prerequisite chain unlock downstream work.

## Apply justified updates without losing history

Edit the discovered authoritative plan/map, not generated outputs or a second status copy. Match existing
formats and supported fields. Reconcile overlapping goal/finish-line summaries deliberately; no implied
sync between project prose, maps, and knowledge stores. Preserve valid completion and evaluation history.

Keep stable project and task IDs for unchanged contracts, including when repository storage changes.
For an authorized migration, update the private index, source paths, links, build selection, and relevant
shared instructions together; preserve provenance and one canonical active source. Do not create a
second task board or assume moving a folder enrolls its projects. When splitting, merging, moving, or
replacing work, retain the original contract/history or an explicit old-to-new identity mapping in the
established notes/log.
Explain what each replacement now proves and update affected dependents, inherited gates, evidence links,
counts, and goal summaries together. Do not transfer a check to a broader/different contract unexamined.
Retain obsolete nodes as the local policy prescribes; an explicit user removal overrides generic retention.
Check the resulting progress denominator: retaining a replaced aggregate as an active leaf alongside
its replacement outcomes double-counts the same work. Use a truthful hierarchy or supported historical/
dropped representation with explicit replacement mappings. Add a separate integration task only when it
has a distinct accepted contract/evaluation, not merely to preserve an old box on the graph.

For ancestry-based browser keys, a move/rename changes edit identity even if the displayed name survives.
Prefer an identity-preserving decomposition when it expresses the work honestly. Record affected paths
and review/resolve existing drafts before applying ambiguous transfers; if drafts cannot be inspected,
flag that limitation and keep old edits from silently attaching to replacements. Never clear user drafts
just to avoid the conflict. The product's current conflict handling is not a migration engine.

## Verify and deliver

Review the actual diff against intent and the initial working state. Validate schema, IDs, references,
cycles, dependency readiness, changed contracts, and preservation of evidence/identity. Run the repository's
required checks plus evaluations relevant to any new claims. Rebuild the authorized local dashboard from
its configured inputs after justified source changes; do not auto-enroll missing sources or hand-edit output.
Verify the expected data reached the derived view and excluded/private material did not. If publication
or an integration is unavailable/out of scope, report the local result and the specific remaining gap.

Give a compact pre/post summary: what was confusing or stale, what changed and why, supporting evidence,
what is clearer/actionable now, and remaining decisions or uncertainty. Report material limitations and
which repositories/checks were covered. Avoid a wall of repository summaries when a small comparison or
visual view communicates the outcome. Local rebuild is distinct from hosted publication.

With unchanged intent/evidence, a second run should preserve authoritative files and avoid gratuitous
task churn, rewritten notes, new audit files, or timestamps. Do not update `touched` merely for reading.
Rebuild only when needed or required by repository instructions; distinguish unavoidable generated build
metadata from plan changes. Report a no-change outcome instead of manufacturing activity.

## Learn from actual feedback

Record actual user feedback and observed workflow problems in the owning private workspace/project notes,
with context and provenance. Separate observation, hypothesis, and accepted principle. Never store personal
findings or project identities in this generic skill or convert guessed preferences into universal rules.

When demonstrated behavior justifies a reusable improvement, make a small targeted change to the canonical
skill source under the maintenance authorization in effect. Preserve unrelated behavior and user scope;
do not silently edit a divergent installed copy. Validate with the bundled skill-creator `quick_validate.py`
when available, and independently forward-test changed mutating behavior on isolated synthetic fixtures,
giving the evaluator the skill, realistic request, and raw artifacts without the expected answer. Compare
the result and an unchanged rerun, then record the feedback/change rationale privately. If maintenance
is not authorized or validation is unavailable, keep a concrete proposal and disclose the limitation.
